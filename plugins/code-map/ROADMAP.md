# 코드 지도 색 체계와 다음 단계 개선 계획서

> 2026-11-19 작성. 단계 A(색·경고 정리)는 이 문서와 같은 변경으로 구현했고, 나머지는 실측 결과를 보고 확정해요.

## Context

사용자 요청 둘: (1) 모호한 색을 쓰지 않게 색 선정을 개선, (2) 다음 단계 개선 계획서 작성.

실제 화면에서 확인한 모호함:
- 상태 알약이 "일부만 읽었어요"인데 **초록**(좋은 상태 색)이고, 바로 아래 카드는 **주황 경고**다. 한 화면에서 신호가 엇갈린다.
- 주황 경고가 **거의 항상 켜진다**. "지도에 넣지 못한 파일 89개"에 문서·이미지 같은 코드가 아닌 파일이 섞여 있어서다. 항상 켜진 경고는 곧 무시된다.
- **파랑이 두 뜻**이다: "눌러서 열 수 있는 파일 이름(링크)"과 "안내/진행 중" 카드 줄무늬.
- 주황 글자가 **갈색**(#8a4b00)이라 주황인지 갈색인지 흐리다.
- 작업 단계(git-stage)가 DSH에 없는 색 변수 이름(`--dsw-alias-state-warning-primary`)을 써서, DSH의 실제 이름(`warn-primary`)과 달라 어두운 테마에서 색이 안 바뀐다.

DSH 앱 번들에서 확인한 사실: DSH의 상태 색은 6종(business 파랑, success 초록, warn 호박색, error 빨강, done 보라, idle 회색)이다. 그런데 DSH의 기본 값은 **글자색으로 쓰면 대비가 모자란다**(흰 배경 위 초록 2.28:1, 호박색 2.15:1, 4.5:1 미달). 그래서 같은 색 계열을 쓰되 글자용은 더 어둡게 잡는다.

## Part 1. 색 체계 (한 색 = 한 뜻, 색만으로 구분하지 않음)

### 원칙
1. **한 색조는 한 가지 뜻만** 가진다. 같은 색을 다른 뜻에 쓰지 않는다.
2. **색 옆에는 항상 아이콘과 글자**가 있다(색각이상·흑백 화면 대비. 초록과 주황은 밝기가 같아서 색만으로는 구분이 안 된다).
3. 경고(주황)는 **실제로 빠질 수 있는 코드**가 있을 때만 켠다. 문서·이미지 같은 비코드는 회색 안내.
4. 모든 글자는 두 테마에서 4.5:1 이상, 아이콘·줄무늬·경계는 3:1 이상(계산으로 확인).

> **2026-11-19 갱신:** 구현하면서 글자색 방식을 채움색 방식으로 바꿨다. 어두운 주황·호박색은 글자로도 배경으로도 갈색으로 보이기 때문이다. 지금은 모든 색을 채움으로만 쓰고 그 위에 읽기 좋은 글자를 얹는다(노랑 `#fbbf24` + `#1f1700` 10.65:1, 파랑·초록·빨강·회색도 5.0:1 이상). 아래 표의 색 값은 설계 당시 값이고, 실제 값은 `lib/client.js`의 `--cm-*`·`--on-*` 변수가 기준이다.

### 뜻 → 색·아이콘·말 (1:1)
| 뜻 | 색 | 아이콘 | 쓰는 곳 | 밝음 글자/틈 배경 | 어두움 글자/틈 배경 |
|---|---|---|---|---|---|
| 진행 중, 누를 수 있음 | 파랑 | 시계, 밑줄 링크 | "읽는 중", 파일 이름 링크, 기본 단추 | `#1d4ed8`/`#eff4ff` | `#8db3ff`/`#1c2a4a` |
| 확인됨 | 초록 | 체크 | "코드는 모두 읽었어요" | `#15803d`/`#ecfdf3` | `#6ee7a0`/`#12301f` |
| 주의(빠질 수 있음) | 주황 | 삼각 느낌표 | 코드가 못 읽힌 범위가 있을 때 | `#b45309`/`#fff7e6` | `#fdb022`/`#3a2a05` |
| 오류·연결 안 됨 | 빨강 | 동그라미 엑스 | 분석 실패, 도구 없음, 연결 확인 필요 | `#b42318`/`#fef3f2` | `#ff8f86`/`#3b1512` |
| 중립·안내·없음 | 회색 | 동그라미 i | "바뀐 게 없어요", 비코드 파일, 꺼짐 | `#475467`/`#f2f4f7` | `#c0c7d4`/`#2a3040` |

검증한 대비비(계산): 밝은 테마 글자/카드(#fff) 파랑 6.7, 초록 5.02, 주황 5.02, 빨강 6.57, 회색 7.69, 글자/틈 배경 최저 4.71. 어두운 테마 글자/카드(#171c27) 최저 7.73, 글자/틈 배경 최저 6.78. 전부 4.5:1 이상.
(파랑은 "안내"로 쓰지 않는다. 안내는 회색. 그래서 파랑 = 누를 수 있음/진행 한 뜻.)

### 화면별 적용 (무엇이 바뀌나)
- **상태 알약**: 읽는 중=파랑+시계, 코드를 모두 읽음=초록+체크, 일부 코드를 못 읽음=주황+삼각, 오류 계열=빨강, 꺼짐=회색. 지금의 "일부 코드 준비됨(초록)"은 없앤다.
- **맨 위 결론 카드**: 줄무늬·아이콘·글자색이 위 표와 같은 한 계열. 코드 모두 읽음+바뀐 파일 있음=초록 체크, 코드 못 읽음 있음=주황, 바뀐 게 없음=회색 안내(지금은 파랑 안내/주황).
- **지도가 못 읽은 범위**: 행을 두 묶음으로 나눈다.
  - "코드로 보이는데 지도에 없는 파일"(`.js .gs .html .py` 등): 개수가 있으면 **주황**, "확인 안 됨"도 주황+물음표 아이콘(없음과 구분).
  - "지도 대상이 아닌 파일"(문서·이미지·백업 등): **회색**, 숫자는 그대로 보이지만 경고가 아니다.
  - 0이어도 "없음"으로 항상 보이는 규칙은 유지(정직성).
- **파일 링크**: 파랑 밑줄 그대로(눌러서 열림). 파랑이 이 뜻뿐이라 안 헷갈린다.
- **작업 단계(git-stage) 요약 칩**: 같은 5색 규칙을 적용. 잘못된 변수 이름 `--dsw-alias-state-warning-primary`를 고치고 어두운 테마를 확인.

### 새로 필요한 데이터 (서버 쪽)
"코드로 보이는데 지도에 없는 파일"을 세려면 `git ls-files`와 지도가 가진 파일의 차이를 확장자로 가르면 된다. 이미 `engine.unknownFormats`가 같은 방식으로 "지도에 한 개도 없는 형식"을 센다. 같은 틀로 `engine.unmappedCode`를 추가하고 `NOT_CODE` 확장자 집합(이미 `lib/engine.js`에 있음)을 재사용. `coverage`에 `unmappedCode`(코드), `notCode`(비코드) 두 숫자를 더한다. 기존 `notIndexed`·`partial`·`unusable`·`unknownFormats`는 그대로 두고 화면 묶음만 바꾼다.

## Part 2. 다음 단계 개선 계획서

실측으로 방향을 정하고(게이트), 그 결과에 따라 만들 것을 고른다. 크기: S 반나절 이하, M 하루 안팎, L 며칠.

### 단계 A. 색·경고 정리 (이번 승인 범위, M)
- 목표: 한 화면에서 신호가 엇갈리지 않고, 경고가 켜지면 정말 확인할 일이 있다.
- 일: Part 1 전부. 서버 `unmappedCode`, 화면 색 체계, 알약, 결론 카드, 읽지 못한 범위 두 묶음, git-stage 칩과 변수 이름.
- 완료 기준: 두 테마·320/375/1280에서 검수 실패 0, 모든 글자 4.5:1, 색 하나가 두 뜻을 갖지 않음(시험으로 상태→색 표를 고정), 흑백 캡처에서도 상태 구분 가능.

### 단계 B. 실측 완료 (사용자 작업 포함, S)
- 현황: 도구 없음/CBM/Trail 세 방식 실험을 시작했지만 첫 두 세션이 복사본이 아니라 코드 지도가 켜진 원본에서 돌아 `plugin` 방식으로 잡혔다(측정 스크립트가 구분하도록 고침, PR #18).
- 일: `gas-exp` 작업 공간 추가 또는 "지도 끄기"로 기준선 1회+, CBM 켜고 3개 요청, Trail 켜고 3개 요청, 방식마다 2회씩. 측정표를 같이 읽는다.
- **결정 게이트**: 아래 C 중 무엇을 만들지 이 결과로 정한다. 표본이 작아 "N배"로 말하지 않는다.

### 단계 C. 지도를 AI가 실제로 쓰게 만들기 (게이트 뒤, M~L)
- C1. MCP가 충분히 줄이면: 우리 플러그인은 MCP 연결 안내·삭제 계열 도구 차단·화면에 집중.
- C2. 아니면 읽기 전용 도구 3개(`graph_find`, `graph_trace`, `graph_snippet`)를 `ctx.tools.register`로 직접 등록(엔진 재사용, 시간 제한, 읽지 못한 범위 한 줄).
- C3. 한국어 요청에도 지도가 붙게: 식별자가 없을 때 CBM의 BM25 검색(`search_graph`의 `query`)으로 후보를 찾아 붙인다(지금은 이름이 있을 때만).
- C4. 파일 요약(시그니처만, 본문의 약 1/10 토큰) 도구.
- 완료 기준: 같은 3개 요청에서 도구 없음 대비 호출·읽은 글자가 줄고 답은 같거나 더 맞다. 줄지 않으면 그대로 보고하고 접는다.

### 단계 D. 학습 노트(Trail 2부) (M~L)
- 새 플러그인 `plugins/learnings`. 파일 형식은 Trail과 같게(`.trail/learnings/*.md`, 머리말 + 결정·배제한 것·주의점) → 나중에 `trail check`를 그대로 쓸 수 있다.
- 일: (1) 사용자가 "이거 저장해"라고 할 때만 저장하는 도구, 개인(`~/.trail`)/저장소 구분, (2) 요청마다 해당 코드의 노트를 앞에 주입(`touches` 경로와 이름 매칭), (3) 고치기 전 충돌 확인("이 결정과 부딪혀요"), (4) 이 컴퓨터 세션 72개에서 두 번 이상 한 말을 규칙 후보로 뽑기(저장은 사용자가 승인), (5) 화면 "기억해 둔 규칙" 카드(쉬운 말, 지우기 쉬움).
- 하지 않는 것: 자동 저장, 팀 서버 연동, 팀원 브랜치 충돌 알림(혼자 쓰므로).
- 완료 기준: 같은 지적을 두 번 하지 않게 되는지 실제 세션 3개로 확인.

### 단계 E. 비개발자 경험 마무리 (M)
앞서 함께 정한 것 중 남은 것: ① 되돌리기 요청 문장 넣기 ② 쉬운 말 결과 카드(바뀐 것·확인한 것·확인 못 한 것·다음 할 일) ③ 검증 신호등(색 체계는 Part 1 규칙 사용) ④ 시작 전 확인 질문 ⑤ **변경 내용(diff) 보기**: 사이드바 파일 열기는 되지만 변경 표시가 따라오는지 앱에서 확인 필요. 턴별 변경 리뷰 화면은 턴 내부 번호가 필요해서 가능성부터 확인.
- 완료 기준: 비개발자 시나리오 3개(고치기 요청→결과 확인→되돌리기)를 처음부터 끝까지 사용자가 직접 해 본다.

### 단계 F. 운영·품질 (S, 틈틈이)
- 측정을 PR마다 돌리는 표로 정리(기준선 고정), README·EXPERIMENT·CHANGELOG 동기화.
- 병합 끝난 작업본 정리(`dsh-feat-code-map-trust`는 이미 삭제, 나머지 4개 남음).
- 위험 점검: DSH 앱 번들의 `sidebarRight`·`tools/post-execute`는 앱 업데이트로 바뀔 수 있으므로 업데이트 뒤 스모크 점검 목록을 문서화. 응답에 저장소 절대 경로(`root`)를 넣은 것은 로컬 화면 전용이므로 원격 접속(휴대폰 작업 공간) 노출 여부 확인.

### 순서와 의존
A는 바로 가능(실측과 무관). B는 사용자 작업이 끼므로 A와 병행. C는 B 결과 뒤. D는 C와 독립이라 B 동안 설계 시작 가능. E의 ③은 A의 색 체계에 의존. F는 계속.
